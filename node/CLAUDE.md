# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

`habarico` is a React UI library for building schema-driven admin dashboards. It auto-generates admin interfaces based on backend-provided schemas, built on top of React Admin (~5.14), MUI v7 and MUI X Data Grid v9 (React 18/19). Published to npmjs.com as the unscoped `habarico`; never move it under `@eluvia`, which maps to the private registry `habarico-enterprise` is installed from.

## Commands

```bash
# Build
npm run build          # Full build (CJS + ESM + type declarations)
npm run prebuild       # TypeScript declaration generation only
npm run watch          # Watch mode (JS + types concurrently)

# Tests
npm run test           # Unit tests (jsdom), run once
npm run test:storybook # Story tests — renders every story in headless Chromium
npm run test:all       # Both projects
npm run test:watch     # Unit tests, watch mode
npm run test:coverage  # Unit tests with coverage report (v8)
npx vitest run src/schema/providers/__tests__/dataProvider.test.ts  # Run a single test file

# Code quality
npm run lint           # ESLint (zero warnings allowed) — includes the import-boundary rule
npm run typecheck      # TypeScript type checking
npm run prettier       # Format code

# Storybook
npm run storybook      # Dev server on port 6006
npm run build-storybook
```

On every pull request GitHub Actions runs `node-code-quality` (lint + typecheck),
`node-unit-tests` (`npm test`) and `node-storybook-tests` (`npm run test:storybook` +
`npm run build-storybook`), defined in `.github/workflows/node.yml`.

The Storybook bucket holds the root build, one `<series>/` copy per minor series and `next/`.
Never prune its root: the series and `next/` live beside it.

## Test Setup

`vitest.config.ts` defines two projects, sharing one `resolve.alias` block via `extends: true`:

| Project | Command | Environment | Tests |
| --- | --- | --- | --- |
| `unit` | `npm test` | jsdom | hand-written, `src/**/__tests__/` |
| `storybook` | `npm run test:storybook` | headless Chromium (Playwright) | one per exported story, generated by `@storybook/addon-vitest` |

Story tests are **smoke tests**: each story is rendered with the decorators from
`.storybook/preview.ts` applied, and fails only if rendering throws. They assert nothing
further unless the story defines a `play` function (none do today). On failure vitest writes a
screenshot to `src/**/__screenshots__/`, which CI uploads as a job artifact.

### Unit project

- **Runner:** Vitest with jsdom environment (`vitest.config.ts`)
- **Libraries:** `@testing-library/react`, `@testing-library/user-event`, `@testing-library/jest-dom`
- **Setup file:** `src/test-setup.ts` (imports jest-dom matchers)
- **Test locations:** `src/**/__tests__/` directories
- **Path aliases** (`@foundation`, `@design`, `@admin`, `@schema`, `@typing`) are available in tests via `vitest.config.ts`
- **Test data is English** — labels, titles, record names, fixture values. The full rule, its
  exceptions and the diacritics/locale traps are in the repository-root `CLAUDE.md` ("Tests").
  Storybook is the exception that matters here: stories and `_data.ts` / `_i18n.ts` / `_shell.tsx`
  stay Czech.

## Storybook

Commands: `npm run storybook` (dev server, port 6006) / `npm run build-storybook`.

Served at [storybook.habarico.com](https://storybook.habarico.com), at the root and under
`/<minor series>/`, published by `.github/workflows/storybook.yml` from `node@X.Y.0` tags. The manager UI
carries the habarico.com branding (`.storybook/manager.ts`, `manager-head.html`,
`.storybook/brand/`); the canvas itself is left alone. **Everything the manager loads must be
addressed relatively** — the same build is served from the bucket root and from a series prefix,
so a leading slash breaks the prefixed copy.

Design-layer components (`src/design/**`) and `admin/**` components follow the same story
standard below. Reference implementation: `design/atoms/Button`; token foundations:
`design/Theme`.

### Structure

- **One component = one autodocs Docs page.** Set `component` + `tags: ['autodocs']`; put prose
  in `parameters.docs.description.component`.
- **Curate the props table.** List only the props that matter in `argTypes`, mirrored in
  `parameters.controls.include` — MUI atoms otherwise dump hundreds of props.
- **`Playground` first, then Showcases.** Export order is display order: `Playground` →
  `Variants` → `Colors`/`Sizes`/`States` (only those that apply). `Playground` is the only
  args-driven story; Showcases are pure `render` matrices demonstrating variations. Pure
  composition components, interaction hooks (`useDialog`/`useMenu`/`usePopover`), and components
  whose real interactivity is a click rather than a Controls change skip the Playground and keep
  a single `Default` story instead.
- **A pure Showcase `render` (a fixed matrix, no args read) may be zero-arity** (`render: () =>
  ...`). Verified against this repo's pinned Storybook (10.3.5): a zero-arity `render` does *not*
  bypass `controls.include`/`exclude` filtering in practice — a curated list still renders curated,
  and an empty `controls.include: []` still renders empty (checked directly in the browser on
  `Button`'s `Variants` and `Table`'s `Default`). Don't chase this as a Controls bug.
- Use the shared kit (`src/design/_storyKit.tsx`: `padDecorator`, `Showcase`, `Row`,
  `VariantGrid`, `SHOWCASE_COLORS`) instead of rebuilding matrix layouts per story.
- A hook that reads theme/context (`useTheme()`, …) must live in a top-level demo component,
  never directly inside a `render` arrow — the "Show code" serializer re-invokes `render` outside
  the theme provider and such a hook crashes there.

### Controls: never a dead or unsafe control

- **No control may be inert.** Setting `component` auto-infers a full `argTypes` table from TS
  docgen whether or not the story reads `args`. If `render` hardcodes everything, either make the
  story genuinely args-driven, or set `parameters.controls.include: []` so the panel honestly
  shows nothing instead of a table that lies. Do this for every curated story, not just ones with
  a Playground.
- **A control only counts if the canvas visibly reacts to it.** Drop from `argTypes`/
  `controls.include` any prop the story's setup can't actually demonstrate, rather than exposing a
  control that changes nothing on screen. Prefer adding the missing setup (decorator/context) over
  deleting the control when that's reasonably possible.
- **A string control backed by a fixed set of valid values (locale, currency, any enum-like
  option) must be a `select`, never free text** — an arbitrary string can crash the component.
  Use `argTypes.<prop>.mapping` when the control's raw value (a boolean switch, a named preset
  key) isn't the literal prop value, so `argTypes` still names the real prop while only ever
  resolving a safe value before `render` sees it. Only offer presets that actually behave
  differently; a preset that silently does nothing recreates the dead-control problem.
- **An `object`/array control needs a real default of the right shape** (e.g. seed a `string[]`
  prop with an actual array) — Storybook infers array vs. map editing from the current value, and
  downstream code (`.map()`, `.join()`) throws on the wrong shape.
- **A prop that changes internal shape, or is only read on mount** (`defaultChecked`, `multiple`
  toggling single value vs. array, …) needs `key={String(args.thatProp)}` on the element so
  Storybook remounts it fresh instead of patching a stale instance.
- A Controls-only `argTypes` entry that re-types a real prop for the panel must not set its own
  `name` override, or the row silently stops rendering.

### "Show code": only real, runnable usage

- **Only `Playground` (or the single no-args story) shows code at all.** Every Showcase sets
  `parameters.docs.canvas.sourceState: 'none'` — a fabricated per-story snippet drifts from the
  real component; hiding the toggle can't go stale.
- **On the one story where "Show code" *is* exposed (`Playground`, or the single `Default` for a
  component without one), its `render` must take an arg parameter.** Verified: a zero-arity
  `render` there makes "Show code" print the story object's literal source text (e.g. `{ render:
  () => <Foo items={fixedData} /> }`) instead of the real, dynamically-serialized JSX. This is the
  one case where the arg-parameter requirement is a real, visible bug, not just a convention — a
  Showcase whose "Show code" is already hidden via `sourceState: 'none'` has no such symptom, so
  don't spend effort chasing zero-arity Showcases for this reason.
- **The snippet must be code a consumer could actually copy and use**, and must reflect what
  really renders (a story mapping over N records shows the `.map()`, not one instance implying it
  multiplies itself).
- **If `render` returns an opaque local wrapper** (needed for local `useState`/context), "Show
  code" only prints that wrapper's tag by default — useless to a reader. Prefer returning the real
  component directly from `render` when possible. When a wrapper is unavoidable, override
  `parameters.docs.source` instead: for a Playground, use `docs.source.transform` — a
  `(code, {args}) => string` that rebuilds the real usage JSX from `args`, staying reactive to
  Controls changes, even if that means injecting the value as pseudo/fake code (see
  `ConfirmDialog`, `InspectorPanel`, `DashboardGrid`, `FormTable`, `UploadArea`, `SettingsPanel`,
  `Search` for the pattern); fall back to a static `docs.source.code` string only when there are
  no controllable args (`code` and `transform` are mutually exclusive — `code` wins if both are
  set). Both live under `parameters.docs.source`, never `parameters.source`.
- A `docs.source.transform` must be idempotent — addon-docs can call it more than once per render,
  so strip any prior occurrence of what you're adding before re-adding it rather than blindly
  prepending.
- `.storybook/preview.ts`'s `parameters.jsx.displayName` resolver (`resolveJsxDisplayName`) is
  what makes "Show code" print real MUI component names instead of `<React.ForwardRef>` — don't
  remove it or override it per-story.

### Documentation content

- **Stories document what the library can do, not how it was built.** Write for a consumer of the
  library, never its maintainer: show capabilities and usage, not fixed bugs, resolved edge
  cases, or how a component behaves differently "now" versus before.
- **Never reference a task/issue number anywhere in a story** (title, description, comments).
- **The Playground story is never duplicated on the autodocs Docs page.** This is already handled
  globally — `.storybook/DocsPage.tsx` (wired via `parameters.docs.page` in
  `.storybook/preview.ts`) sets `<Stories includePrimary={false} />` to drop Storybook's default
  second, static copy of the primary story. Don't remove this, revert to the default template, or
  reintroduce the duplicate some other way.

### Misc

- Story titles follow `design/<tier>/<Name>` (or `admin/<tier>/<Name>`), matching the folder.
  Sidebar order is set in `.storybook/preview.ts` (`storySort`).

### Schema-layer stories (HAB-878)

A schema component is **not configured by props but by schema**, so the design-layer standard does
not transfer literally. Schema-layer component stories (`src/schema/components/**`) follow this one:

- **No `args` / `argTypes` / Controls — for now.** A schema component is driven by the *schema* and
  by the contexts around it, not by its props: a box takes its read-only mode from
  `ViewSchemaContext`, a field its renderer from the provider chain. Controls wired to a story-local
  arg therefore look interactive and change nothing, which is worse than no Controls at all. Every
  story is a plain `render` showcase and sets `parameters.controls: {disable: true}`. Re-introducing
  a Playground is fine **only** once the arg demonstrably changes the canvas — verify it, do not
  assume it (`?args=readOnly:true` on the story's `iframe.html` is enough to check).
- **Export order is display order:** the plain case (`Default`, or the dispatch matrix `FieldTypes` /
  `BoxTypes` / `InputTypes`) → states (`ReadOnlyAndWritable`, `EmptyValue`) → the named edge cases.
- **One component = one autodocs page:** `component` + `tags: ['autodocs']`. Type the meta as
  `const meta = {...} satisfies Meta;` and the stories as `type Story = StoryObj;` — binding
  `StoryObj` to the meta makes the component's required props mandatory `args` on every story, which
  a `render`-only story does not have.
- **`layout: 'padded'`** on every story, like the design layer. The global default in
  `.storybook/preview.ts` is `fullscreen`, which renders a schema story flush against the canvas edge.
- **Never build the context ring inline — use `src/schema/components/_storyKit.tsx`.** It provides
  `makeSchemaRoot()` (a fully typed `SchemaRootContextState`, so no `as unknown as` stubs),
  `SchemaStoryProviders` (the whole ring: router → `CoreAdminContext` → locale → admin config →
  `TabsLocationProvider` → schema root → resource → record → local resource schema → method schema →
  view schema → optional `Form`), the three decorators `withSchemaFieldShell` / `withSchemaInputShell`
  / `withSchemaBoxShell`, and the `Showcase` / `ShowcaseStack` matrix helpers. Override any level per
  story from `parameters.schemaStory` (`record`, `viewSchema`, `resource`, `list`, `width`, …).
  Fixtures live in `src/schema/components/_data.ts` — piece-shaped fragments on the e-shop domain the
  documentation pages use, as opposed to the page-shaped `schema/pages/_data.ts`. Neither file is
  exported from the barrel.
- **Story tests pass even when a component crashes** — Storybook's `RenderErrorBoundary` catches the
  throw and vitest still reports a pass. A green `npm run test:storybook` is therefore **not**
  sufficient: check the run's output for `The above error occurred in the <Component>` too. This is
  how a missing context provider hides (a tab box without `TabsLocationProvider`, a list slot without
  `ListConfigProvider`). It also hides the **datagrid preference-key loop**: every story of a file
  renders into the same browser page, so two datagrids sharing one `preferenceKey` but showing
  *different columns* hand each other a stored column set that does not fit and resize until React
  gives up ("Maximum update depth exceeded"). The kit keys each story by its own story id, which
  covers the usual case; a single story that mounts two differently shaped datagrids has to split
  into two stories (see `SchemaDatagrid`'s `WithoutRowActions`) or pass its own
  `schemaStory.preferenceKey`.
- **A story shell must bring its own React Admin store.** `CoreAdminContext` falls back to a
  module-level `memoryStore()` *singleton* shared by every instance on the page, and
  `StoreContextProvider` empties it on `setup()` (mount) as well as `teardown()` (unmount). An
  autodocs page mounts one `CoreAdminContext` per story, so each mount wipes what the earlier ones
  stored — and anything reading RA preferences renders as if nothing had been configured. It is
  invisible in single-story view and invisible to `test:storybook`; the way it surfaced was a
  `SchemaDatagrid` docs story with **no columns**, which came back as soon as you interacted with the
  grid. `SchemaStoryProviders` passes a per-mount `memoryStore()`; keep it that way, and do the same
  in any new shell that boots `CoreAdminContext` by hand.
- **A collection with `indexField` set forces the sort onto that field** rather than waiting for it,
  so a story cannot demonstrate "dragging is off because the sort differs" — the reachable off-switch
  is a `sortForFilters` mismatch. Check what the component actually does before writing the caption;
  a story that states a rule the code does not have is worse than no story.
- **Cross-cutting concept stories** — one that documents a rule rather than a component (the action
  slots in `schema/boxes/BoxActions`, the five view slots in `schema/views/ViewSlots`) sit beside the
  concern they explain and take no `component`.
- **Deliberately not given component stories:** `SchemaAdmin`, `SchemaResource`, `SchemaLayout`,
  `SchemaViewRouter` and the view shells (`SchemaList` / `Show` / `Create` / `Edit` / `Action`) — the
  `schema/pages/*` stories boot a real `SchemaAdmin` and **are** their story; a component story would
  only re-boot the whole admin. Contexts, hooks, providers and the `dynamic/` wrappers are non-visual
  and belong in unit tests.
- A story is only finished when its documentation page carries the matching
  `storybook: <story-id>` front matter (see [Documentation](#documentation)).

## Architecture

`src/` is split into **four architectural layers**, with dependencies flowing **strictly downward**:

```
schema   →   admin   →   design   →   foundation
(schema-driven) (React Admin + our skin) (pure MUI presentation) (non-visual kernel)
```

| Layer          | `src/…`      | What it is                                                                                    | Reference                                              |
| -------------- | ------------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| **foundation** | `foundation` | Non-visual shared kernel: pure utils, i18n data, plain navigation hooks. **No MUI/RA/schema.** | [`src/foundation/README.md`](src/foundation/README.md) |
| **design**     | `design`     | Presentational, schema-agnostic design system (atoms / molecules / organisms + theme).        | [`src/design/README.md`](src/design/README.md)         |
| **admin**      | `admin`      | React Admin restyled into the design system — resource-aware but **schema-agnostic**.         | [`src/admin/README.md`](src/admin/README.md)           |
| **schema**     | `schema`     | The schema-driven core — reads a Habarico schema and generates the whole admin UI.            | [`src/schema/README.md`](src/schema/README.md)         |

**Each layer's `README.md` is the authoritative reference** for that layer — its purpose, fixed
directory structure, entry point and internal mechanisms. **Read the relevant one before adding or
moving code.** The layer-specific architecture is documented there, not here: the `SchemaAdmin` /
`BaseAdmin` entry points, the schema-driven UI generation, the customization-provider system, the
schema context ring, the dashboard & widgets, forms (drafts / navigation guard), view routing and
search highlighting.

A layer may import only itself and the layers **below** it; importing "up" is an architecture
violation and **fails `npm run lint`** via the `boundaries/dependencies` rule (see
[Code structure & conventions](#code-structure--conventions) and `eslint.config.mjs`). This is the
result of HAB-668; the old top-level per-concern folders (`components/`, `hooks/`, `providers/`, …)
no longer exist.

### Entry points

- `src/index.ts` — the package entry; spreads the four layer barrels plus the root types.
- `src/schema/types.ts` (`@schema/types`) — the core schema type definitions (`ServiceSchema`,
  `ResourceSchema`, `HabRecord`, the `FieldType` / `FieldFormat` / `BoxType` / `ViewType` unions, …).
- `src/types.ts` (`@typing`) — a small root type aggregation (`ServiceConfigMap`, `IconsMap`, …),
  distinct from the schema layer's `@schema/types`.

## Code structure & conventions

These rules keep the layered architecture (above) intact. Several of them exist because they were
repeatedly violated during the HAB-668 refactor — treat them as hard requirements, not style.

### Layering

- **Dependencies flow downward only:** `schema → admin → design → foundation`. Importing "up"
  fails `npm run lint` (the `boundaries/dependencies` rule in `eslint.config.mjs`).
- **To fix a violation, move the shared thing _down_, don't import up.** If an `admin` file needs a
  type from `schema`, the type is in the wrong layer: put the generic version in the lowest layer
  that needs it and let higher layers import it. Example: `LinkTarget` lives in
  `@foundation/utils/navigation`; the generic `SearchObjectHighlight` and `AdminRecord` live in
  `@admin`; the schema layer's richer `HabRecord` is a structural **superset** of `AdminRecord`, so
  a schema record is still assignable where an admin record is expected — no upward import needed.
- Before adding or moving a file, read the target layer's `README.md` — each one fixes the
  directory structure and states what belongs there.

### Folders & barrels

- **One folder per component / hook / context, with its own `index.ts`** that re-exports it. The
  layer's root `index.ts` (`@admin`, `@schema`, …) re-exports the public members from each area.
  _Exception:_ the `design` tier directories (`atoms` / `molecules` / `organisms`) have **no**
  `index.ts` — the design barrel re-exports leaf modules directly and code imports them by full
  sub-path (`@design/atoms/Chip`).
- **Within a layer, import a sibling by its sub-path — never through the layer barrel.** Importing
  your own layer's `index.ts` from inside the layer creates import cycles and load-order bugs. Use
  `@admin/components/buttons/ActionButton`, not `@admin`, from inside `admin`.
- **Single-source every public name.** `src/index.ts` spreads all four layer barrels with
  `export *`. When two barrels export the **same name**, ES `export *` makes it _ambiguous and
  silently drops it from the combined namespace_ — the symbol vanishes from the public API with **no
  error**. So when you relocate a symbol, **move** its public export; do not re-export the same name
  from two barrels that a higher barrel spreads. If a lower-layer symbol must stay importable via a
  deep alias (e.g. `@schema/types` re-exporting the admin `SearchObjectHighlight` for back-compat),
  re-export it there but **not** from that layer's public barrel, so the root sees it once.
- **Don't export non-components from a component file** (`react-refresh/only-export-components`).
  Constants, context objects and pure helpers that sit next to a component go in a sibling
  `constants.ts` / `context.ts` / `utils.ts`; the folder's `index.ts` re-exports both. Splitting the
  `use*Context` hook + `Context` object (a `.ts`) from its provider component (a `.tsx`) is the
  standard fix for the mixed-export warning.
- **Resolve barrel name-collisions by _not_ re-exporting** (sub-path only). E.g. the schema
  `Resource*Context` provider components share names with the customization-provider _types_, so they
  are intentionally kept out of the barrel and imported by sub-path.

### Aliases

- Keep the alias maps in `tsconfig.json`, `vitest.config.ts` and `.storybook/main.ts` **in sync** —
  add a new alias to all three. There is one alias per layer (see [Path Aliases](#path-aliases)).

## Documentation

User-facing documentation lives in `docs/` **here, beside the code** (rendered as
docs.habarico.com/node), **not** in `README.md` — that file is a quick start and stays one. A
change to the public API is finished when its page is updated, in the same merge request as the
code: the page is published from the release tag, so one merged later is one the reader does not
get until the next release.

Read `CONTRIBUTING.md` in the `hab-docs` repository before writing a page; it fixes the page
templates and the e-shop example domain. Where things go:

| What changed | Page to update |
|---|---|
| A prop on `SchemaAdmin` / `SchemaResource` | `docs/base-components/` |
| A provider or its default implementation | `docs/providers/` |
| A field, input, box, layout or view component | `docs/{field,input,box,layout,view}-components/` |
| A hook | `docs/hooks/` (plus the table in its `index.md`) |
| A schema type the backend sends | `docs/types-and-schemas/` |
| Anything a paid component does | `node-enterprise/docs/` in `habarico-enterprise`, same path |

A new design-layer component needs both: its story (see [Storybook](#storybook)) and a page whose
front matter carries `storybook: <story-id>`, the id Storybook builds from the story `title` plus
the export name (`design/atoms/Button` + `Playground` → `design-atoms-button--playground`). Run
`npm run capture:stories` in a checkout of `hab-docs` for the screenshot — it lands beside the page
here, ready to commit — and `npm run check:stories` to verify the id resolves.

The four `src/*/README.md` files are the exception: they document the internal architecture of each
layer for whoever works **on** the library, and stay in the repository.

**Verifying a page.** The site is built in a checkout of `hab-docs`, which reads the pages from
here:

```bash
cd <hab-docs>
HABARICO_PATH=<this monorepo> npm start   # dev server on :3000, or
HABARICO_PATH=<this monorepo> npm run build   # fails on a broken link
```

`onBrokenLinks: throw` covers the whole site, free and premium pages together, so a renamed heading
or a moved page fails here rather than at publish time. The `docs-check` workflow runs the same build on
every pull request that touches `*/docs/**`.
